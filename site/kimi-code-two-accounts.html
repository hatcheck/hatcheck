Kimi Code CLI with two accounts

Moonshot's Kimi Code CLI, kimi, keeps its login, settings and sessions in ~/.kimi-code. KIMI_CODE_HOME moves the whole home, so a second account is a second home, ~/.kimi-code-work, signed in once there, exactly as Codex's are. Hatcheck adds ck to run kimi with a home, and lists every home's sessions and plan windows beside Claude Code's and Codex's.

The variable itself

mkdir -p ~/.kimi-code-work
KIMI_CODE_HOME=~/.kimi-code-work kimi login     # sign that home in, once
KIMI_CODE_HOME=~/.kimi-code-work kimi           # Kimi Code CLI with that account

With hatcheck

Install the CLI, and ck does the above, making the folder on first use:

ck work login               # sign in once, with that account
ck work                     # Kimi Code CLI with ~/.kimi-code-work
ck work --session <id>      # one of that home's sessions
cd ~/code/api
hatcheck bind work          # here, plain ck means ck work, and cl and cx the same
hatcheck                    # the sessions here from every home and profile, with the command that resumes each

hatcheck usage shows each home's Kimi Code plan windows, the 5-hour and 7-day ones and the month's, from the endpoint kimi's own /usage asks, with the access token kimi saved in the home sent as it is and never refreshed. That token lasts a quarter of an hour and kimi renews it as it runs, so a live reading needs kimi to have run recently; otherwise hatcheck's last reading is shown with its age. hatcheck move carries a session between Kimi homes whole, as it does between Codex homes, or converts it for Claude Code and the others, and theirs for kimi; quit kimi first, since nothing marks a Kimi session open.

What hatcheck never does

It never asks for, copies, refreshes or moves a login: ck work login is kimi's own sign-in, in your terminal. It is never between kimi and Moonshot, runs nothing in the background, and switches no account on its own. Each rule, with the code that keeps it: rules it keeps.
